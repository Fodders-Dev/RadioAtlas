# Лира: рекомендации относительно текущего источника

01.10.2026. Это проверенный по коду бриф следующего участка этапа 5 дорожного
плана. Код этого участка ещё не реализован; ответы настоящего провайдера
не оценивались. Аудит Astra read-only, Sol отвечает за дальнейшую реализацию.

## Найденный разрыв

`ChatSheet.tsx` уже отправляет UUID выбранной/текущей станции, имя/трек,
вкусовой контекст, очередь и подтверждения действий. `aiRoutes.ts` принимает
этот контекст. В `ai/brain.ts` детерминированные вопросы о станции и треке
используют его; lookup станции проверяет факты через существующий getStation.

Но transcript обычного discovery-planner строится из истории и текста
пользователя, без нынешней станции. Даже итог наблюдения lookup/search
сокращён до имён: страна и теги теряются. Поэтому «такое же из другой страны»
может не иметь реальной опоры, хотя транспорт уже прислал нужный UUID.

Существующие tools умеют каталог и lookup; политика проверяет допустимые
действия. Проверенное наличие stream URL не подтверждает здоровье потока.
Сохранённые находки не входят в ChatInput: вкусовые счётчики не заменяют их.
В шести fixture-запросах eval нет сценария относительно текущего источника;
stub поиска игнорирует страну. Не запускать платный eval как доказательство
качества нового сценария без исправления фикстур и согласованного бюджета.

## Один следующий участок

Помочь найти станции с родственными **каталожными жанрами в другой стране**.
Не обещать «такой же трек» или измеренную спокойность: акустических данных нет.
Сначала сделать контекст текущего источника фактическим и доступным планировщику;
затем обеспечить ограничение результатов, а не только написать его в prompt.

1. Разрешать источник по UUID через существующий инструмент каталога. Имя,
   страна и теги из browser display strings не становятся доверенными фактами.
2. Передать ограниченный набор проверенных полей как данные. Не включать
   сырые provider-объекты, URL/HTML описания или инструкции из тегов.
3. Для явного «другая страна» отсеивать сам источник, ту же/неизвестную страну
   и жанрово несвязанные кандидаты. Не ослаблять условие после пустого ответа.
   Если ограничения должны применяться до cap поиска — расширить внутренний
   provider-фильтр, а не фильтровать первые три результата и терять остальные.
4. Возвращать реальные station cards и короткую причину по каталожным данным.
   Рекомендация/запрет играть не запускает звук. Явное Play остаётся под
   существующей политикой действия и только для допустимой возвращённой станции.
5. Не менять отключённую AI, обычные диалоги и детерминированные Q&A.
   Продолжение «другая страна» сохраняет источник по UUID, не по догадке.

Вероятные файлы: небольшой helper в `apps/api/src/ai/`, `brain.ts`;
при необходимости `types.ts`, `tools.ts`, `catalogToolProvider.ts`.
Новый payload браузера этому сценарию не нужен. Чтение server .env/data,
платные model/API calls и публикация не нужны для локального этапа.

## Доказательства до настоящего провайдера

- Источник джаз/Франция; кандидаты: он сам, французский джаз, немецкий/японский
  джаз, немецкий рок, джаз с неизвестной страной. Пройдут только подтверждённые
  иностранные жанрово связанные источники.
- `ai.brain.test.ts` со stub fetch: lookup использует переданный UUID, поиск
  опирается на проверенную страну/жанр; ошибочный ответ модели не обходит фильтр.
- Нет UUID, lookup не удался, нет страны/музыкальных тегов, пустой результат:
  честное отсутствие опоры, без перехода к произвольным популярным карточкам.
- История/продолжение, неверное display-name, явный запрет Play, разрешённый
  Play, отказ провайдера; существующая телеметрия ошибки сохранена.
- Если введён фильтр provider — fixture с множеством домашних станций перед
  подходящими иностранными: валидные результаты не теряются перед cap.

API source/test typecheck и test:api обязательны для изменения server AI.
При изменении webapp — также unit и функциональный браузерный gate.
Не выдавать такие проверки за качество настоящей модели или слышимость радио.
