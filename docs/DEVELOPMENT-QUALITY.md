# Проверяемая готовность RadioAtlas

Введено 09.10.2026 по просьбе владельца. Цель — раньше ловить потерю звука,
личных данных и бесполезные ответы, сократить повторные прогоны и передачу
устаревших решений. Здесь критерии доказательств; текущая работа — в PLAN.md,
краткая передача — в WORKING-SETUP.md. Дополнительные плагины не требуются.

## Одна команда, разные уровни

Из корня checkout, Node >=24:

```powershell
npm.cmd run verify -- --dry-run
npm.cmd run verify -- --profile fast
npm.cmd run verify -- --profile release
```

- `fast`: оба typecheck, API, bot, ops scripts и webapp units. Это также
  обязательный быстрый job CI. В отличие от `npm test`, webapp units включены.
- `release`: fast + fixture-only Lira evaluation + build + functional Playwright
  с одним worker и `PLAYWRIGHT_SKIP_PIXELS=1`. Полный браузерный прогон на этой
  машине запускать только один; занятые порты не освобождать без проверки владельца.
- `--dry-run`: только план; не доказательство прохождения проверок.
- `--output .tmp/my-verification`: отдельная папка отчёта и логов.

По умолчанию отчёты находятся под игнорируемой `.tmp`. JSON и Markdown фиксируют
HEAD, ветку, рабочие изменения, команды, результаты и длительности. Первая
ошибка останавливает последующие шаги; NOT_RUN не считается успехом.
Сравнивать начальное и конечное состояние checkout: тесты во время изменения
исходников не подтверждают итоговый diff. Отчёт грязного checkout относится к
HEAD + перечисленным рабочим изменениям, а не к опубликованному коммиту.

Во время итерации достаточно нужного узкого теста. Полный профиль не надо
повторять после каждого комментария или ради красивого отчёта. Перед завершением
действуют требования CLAUDE.md; новые изменения/ошибка обосновывают повтор.
Автоматические проверки не подтверждают удобство дизайна, настоящий звук,
доставку команд iOS и качество настоящей модели. Эти слои записывать отдельно.
Логи тестов не являются автоматически очищенными от любых чувствительных данных:
не публиковать их за пределами приватного рабочего процесса без просмотра.

Для живого Lira-прогона сохранить диалог целиком: исходный запрос, уточнение,
реакцию и фактические карточки/actions. Добавить несколько новых формулировок,
которых не было в фикстурах. Отдельно оценивать исполнение и полезность: есть ли
действие, соответствует ли ограничению, правдивы ли объяснения, хочется ли
пользоваться ответом. Один удачный ответ из нескольких — не стабильность.
Платные вызовы — только в согласованном бюджете; эти профили их не запускают.
Production аккаунты/библиотеки не изменять ради теста без отдельного согласования.

## Независимая проверка

Для замечания нужны место, конкретный вход/состояние, плохой результат и способ
воспроизведения. Отделять доказанную ошибку от гипотезы и предпочтения.
Для аудио, синхронизации и существенной AI-логики проверять вызывающий код,
данные фикстуры и границу настоящего адаптера. Если регрессия важна, показать,
что тест падает на старом поведении или при целевой подмене (mutation check).
Один автор реализации; main проверяет diff независимо. GPT-6 Luna кодит,
main планирует/проверяет, Astra привлекается для существенного риска.

Для UI действуют DESIGN-DIRECTION.md §0 и правило владельца:
сделал → прошёл сценарий человека → исправил неудобное/некрасивое → продолжил.
Просматривать реальный экран телефона/планшета/ПК, пустое/ошибочное состояние,
главное действие и возврат. Согласие другой модели и снимок сами по себе не приёмка.

## Передача и выпуск

WORKING-SETUP.md содержит только checkout/ветку, последнюю подтверждённую
production-версию, принятые ограничения, открытые риски и один следующий шаг.
Хронология живёт в отчётах; при сжатии контекста сначала сохранить незавершённое
состояние. Исторический документ не становится действующей инструкцией.

Локальный отчёт не разрешает deploy. Сохраняются same-SHA обязательные CI jobs,
проверка deploy и публичного bundle/health. Новую композицию нельзя публиковать
без просмотра владельцем. Для инструментального участка достаточно нужных
скриптовых проверок и обоих typecheck; браузер запускать при затронутом поведении.

Через три следующие законченные продуктовые задачи оценить пользу:
какие реальные дефекты пойманы до выпуска, что вернул владелец после выпуска,
сколько полных повторов было необходимо. Расход токенов/время записывать лишь
при наличии измерений. Новые инструменты добавлять под обнаруженный пробел.
