# Личная библиотека, полная очередь и восстановление радио

05.10 владелец сообщил три конкретных сбоя: добавления в плейлист с телефона
не видны на ПК; после фоновой паузы/звонка системный Play не возвращает радио;
из примерно 200 избранных в очереди остаётся 120.

`e2c8dbf` перенесён на актуальный production master `3c3710a` в ветке

используют существующие production-кнопки и строки очереди.

## Что исправлено

**Очередь.** Общая нормализация станций обрезала любой переданный набор до 120.
Теперь явная очередь сохраняет весь набор после удаления повторных UUID:
Listen, Shuffle, выбор последней строки, восстановление после reload и Лента
работают с теми же 200 станциями. Ограничение 120 оставлено только для
автоматического пополнения личного радио. Серверный лимит избранного 200 и
лимиты плейлистов (24 набора, 128 станций в наборе) этим изменением не отменены.

**Синхронизация.** Раньше библиотека объединялась только при первоначальном
входе в аккаунт; уже открытый ПК не подтягивал её при возвращении. Полный PUT
устаревшей копии мог затем затереть изменения телефона. Теперь видимый клиент
подтягивает библиотеку при focus/pageshow/online/visibilitychange и каждые
60 секунд, с защитой от повторного запроса в пределах пяти секунд. Нет
фонового polling для скрытого приложения. Ошибка сети не удаляет вход/данные.

Новый клиент передаёт revision сохранённого содержимого. Сервер сравнивает её
перед записью; при 409 клиент переносит локальные изменения на свежую копию.
Одновременные добавления внутри одного плейлиста сохраняются с обеих сторон;
удаление прежнего элемента не воскресает из неизменной старой копии. Позиция
очереди и аудиоисточник от получения библиотеки не меняются.

Редактирование фиксируется сразу, без прежнего окна 1.4 секунды, в котором
ответ на старое добавление мог отменить новое удаление. Отправка по-прежнему
объединяет быстрые переключения за 1.4 секунды, чтобы не создавать PUT на каждый
свайп. Запросы последовательны; правки во время запроса заменяют ожидающий снимок.
Пользовательское намерение
и серверный транспорт хранятся отдельно. Проверены отмена до ACK, потерянный
ACK после реально принятой записи, ошибка до принятия записи, повторный вход,
задержанный GET, несколько правок во время 409 и ошибка повторного PUT.
Неподтверждённая запись повторяется при возвращении/восстановлении сети.

При проверке на настоящем локальном API обнаружен и исправлен цикл PUT:
объединение профилей вкуса повторно складывало уже учтённые оценки. ACK теперь
идемпотентен; при независимых правках прибавляется локальная разница относительно
общего основания. Browser regression также ограничивает число записей, чтобы
зелёный конечный список не скрывал бесконечную нагрузку на сервер.

**Пауза/возобновление.** Нативная пауза (включая фазу подключения) теперь
фиксирует остановку с сохранением выбранной станции и источника. Ошибка,
ended или завершение звонка сами по себе не дают разрешение снова играть.
Явный Play может заново подключить застывший поток даже при ложном
`paused=false`, а также возобновить AudioContext в состоянии interrupted.
Повторный Play не перезапускает живой или уже подключающийся поток.
Внутренние pause при смене источника отделены от внешней паузы.
Мобильный Apple WebKit выбирает нативный транспорт также с CriOS/FxiOS/EdgiOS
в UA; это не утверждение об actual UA установленного приложения владельца.

## Честные ограничения

- Физический iPhone 11/системный плеер/автомобиль не проверены. Browser harness
  вызывает зарегистрированные MediaSession handlers; он не доказывает доставку
  Play системой в приостановленное Home Screen приложение. Нужен реальный
  прогон с опциональной диагностикой по RUNBOOK. Этот сбой нельзя объявить
  полностью закрытым только по Chromium и unit-тестам.
  ADB проверен 05.10: список подключённых устройств пуст; физический Android
  в этом проходе также не проверен.
- Старый клиент без baseRevision остаётся совместимым, но его полный PUT ещё
  не защищён от конфликта. Защита требует нового клиента и API вместе.
- Журнал неподтверждённых намерений пока в памяти сессии. Полный reload/закрытие
  до успешного сохранения не равны надёжной offline-синхронизации. Первичный
  merge при входе остаётся прежним; durable tombstones/операционный журнал
  для конфликтов после перезапуска — отдельная работа.
- Историческое исчезновение двух конкретных станций владельца не восстановлено:
  нет их UUID/доказательства, были ли изменения сохранены сервером или затёрты.
  Исправление защищает дальнейшие изменения, не выдумывает утраченный состав.
- В исходной рабочей ветке есть непринятая клиентская композиция; целиком она
  не публикуется. Для выпуска поведенческие исправления отделены от неё.
