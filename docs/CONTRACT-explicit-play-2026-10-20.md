# Контракт: Play с блокировки не должен убивать здоровый поток

Задан 20.10.2026 по **трассе с iPhone владельца**, снятой на проде `f4ef231`.
UA сообщает iOS 18.7 / Safari 26.6.1; standalone PWA,
`audioContextState: null`. Точная версия ОС отдельно в этой записи не измерена.
Это не гипотеза: ниже числа из самой записи.

## Что показала трасса

Отсчёт от начала записи.

| время | событие | видимость | paused | currentTime | readyState |
| --- | --- | --- | --- | --- | --- |
| +10.259 | `audio_progress` | visible | false | 17.7 | 4 |
| +15.109 | `visibilitychange` | **hidden** | — | — | — |
| +18.405 | **`media_pause_command`** | hidden | false | **25.9** | 4 |
| +18.429 | `audio_pause` | — | true | 25.9 | 4 |
| +20.724 | **`media_play_command`** | hidden | true | 25.9 | 4 |
| +20.758 | **`audio_emptied`** | — | false | **0** | **0** |
| +20.759 | `audio_waiting` | — | false | 0 | 0 |
| +24.621 | `audio_stalled` | — | false | 0 | 1 |
| +25.973 | `visibilitychange` | **visible** | — | — | — |
| +26.779 | `audio_playing` | — | false | 0 | 4 |

Четыре факта, каждый прямо из таблицы:

1. **iOS доставляет команды.** `media_pause_command` и `media_play_command`
   пришли при `visibility: hidden`. Версия «обработчики, зарегистрированные до
   первого звука, выбрасываются iOS» для play/pause **закрыта** — они дошли.
2. **До паузы позиция продвигалась.** Между снимками прошло 8.146 секунды,
   позиция выросла 17.7 → 25.9. Этот интервал включает видимое состояние;
   от перехода в фон до команды Pause прошло 3.296 секунды. В момент Pause
   `readyState` был **4**, ошибок нет.
3. **Пауза длилась 2.3 секунды.**
4. **Через 34 мс после Play наш код опустошил элемент.** `audio_emptied`,
   `readyState` 4 → 0, `currentTime` 25.9 → 0. Это `audio.load()` из
   `attachSource`, вызванный путём восстановления.

Итог: **6.055 секунды до `audio_playing`** от нажатия Play; событие пришло лишь
через **0.806 секунды после возврата приложения на передний план**. Пока
страница была скрыта, переподключение не доехало — буферизация, затем `stalled`
на `readyState: 1`.

## Причина

`apps/webapp/src/lib/useAudioPlayer.ts`, в `resume()` (строки ~2027–2034 на
`origin/master`):

```ts
if (audio.paused && currentRef.current &&
    document.visibilityState === 'hidden' && !unresolvedRecoveryDebt()) {
  backgroundResumeEligibleRef.current = { … };
}
```

Условие **не проверяет здоровье источника вообще**. Любой Play со скрытой
страницы объявляет сокет подозрительным и уходит в полное переподключение —
двухсекундная пауза на идеальном потоке с `readyState: 4` получает ровно то же
обращение, что мёртвый сокет. В этой записи переподключение со скрытой страницы
не завершилось до возврата на передний план; причина задержки сети отдельно
не измерена.

**Связь с «радио пропало из плеера» требует проверки на устройстве.**
Опустошение источника — кандидат на причину потери системной карточки, но
журнал не снимает сам интерфейс Now Playing. `hasMetadata` остаётся `true`:
это наш объект `MediaMetadata`, а не доказательство видимости карточки iOS.

⚠ Это правка `a653d54` от 05.10, которая чинила реальный дефект: раньше долг
выдавался только при возврате в приложение, и Play с блокировки падал в голый
`play()` по мёртвому сокету. Лечение верное по направлению и слишком широкое по
условию. Мы не возвращаемся назад — мы добавляем недостающую проверку.

## Контракт

**Переподключение назначает наблюдаемый отказ, а не видимость страницы.**

1. Явный Play сначала пробует `play()` на существующем источнике, если элемент
   ещё держит медиа: нет `error`, `readyState` достаточен, буфер покрывает
   текущую позицию.
2. Переподключение происходит только тогда, когда позиция **не сдвинулась** за
   обычное окно сторожа после этой попытки — то есть по доказанному отказу,
   а не заранее.
3. Видимость страницы перестаёт быть основанием для переподключения. Она может
   влиять на срок ожидания, но не на само решение.
4. Долг восстановления, выданный по доказанному отказу, работает как сейчас:
   ходит только по кандидатам **той же** станции, очередь и фид недостижимы,
   политика #86 не затрагивается.
5. Повторный Play остаётся идемпотентным: одна попытка — одно переподключение.
6. **`01a233a` складывается в этот же срез.** Его случай (элемент не на паузе,
   позиция заморожена весь интервал сторожа) — это и есть «доказанный отказ» из
   п.2, то есть частный случай общего правила. Два разных условия выдачи долга
   в одной функции — это то, из чего вырос нынешний дефект.

## Приёмка

1. **Главная, из трассы:** станция играет, экран заблокирован, пауза с плеера
   iOS, через 2–3 секунды Play. Звук возвращается **не выходя из блокировки**,
   `audio_emptied` в трассе отсутствует, карточка из плеера не пропадает.
2. **Долгая пауза:** та же проба, но пауза больше минуты. Звук возвращается;
   переподключение допустимо, если потребовалось, и подтверждается движением
   позиции.
3. **Мёртвый сокет:** поток, который перестал отдавать данные в фоне, по Play
   переподключается — поведение `01a233a` сохраняется.
4. Станция при любом из этих путей не меняется ни разу.
5. Повторные нажатия Play не плодят переподключений.
6. Юниты на выбор ветки: здоровый буфер → `play()` без `load()`; замороженная
   позиция → `load()`. Существующие тесты `useAudioPlayer.resumeWiring` не
   ослаблять, а дополнять.

**Доказательством считается новая трасса с телефона владельца, а не зелёный
прогон.** В отчёте приводить таблицу вида «время / событие / paused /
currentTime / readyState», как выше.

Каждая по своему коду выхода. Ни одна из них не доказывает звук на iPhone.

## Чего не делать

- Не возвращать поведение «Play с блокировки всегда играет голым `play()`» —
  это дефект, который чинил `a653d54`.
- Не добавлять тихое keepalive-аудио и не превращать паузу в stop: в RUNBOOK
  это уже записано как запрещённое по прошлому разбору.
- Не трогать `MediaMetadata` и регистрацию обработчиков: трасса доказала, что
  команды доходят. Это не та поверхность.
